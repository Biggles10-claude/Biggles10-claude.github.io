"Ubuntu makes Strix Halo 33% faster than Windows": fact-check

David Hendrickson (@TeksEdge, posted 11:00 AWST Sat 10 Oct 2026) summarised a Hardware Busters retest of the BOSGAME M5. I checked every number against the original article and compared it with other public Strix Halo benchmarks.

Verdict: partly trueSource numbers: all accurateGeneral conclusion: overstatedOne model · one machine · 3 runs
Verdict: partly true. Every number in the post matches the Hardware Busters article (published 06:23 AWST Thu 8 Oct 2026). On the same BOSGAME M5, with Qwen3.8 27.3B Q8 and a 96 GB graphics allocation, a long answer took 37.94 s on Windows 11 and 25.27 s on Ubuntu 26.04.1 with llama.cpp on Vulkan/RADV. That is 33.4% less time, and the first text came 11.3 s sooner. The post goes wrong when it treats this as an OS-only effect and as a general rule. The author himself says that the OS, the graphics driver and the llama.cpp build all changed between runs. He also says he didn't keep every Windows launch setting, and he never says which llama.cpp GPU backend Windows used. Almost all of the gain came from reading the prompt (prefill). Writing speed rose only 9.5% (15.22 to 16.66 tok/s). Other public benchmarks show the Windows-vs-Linux winner flips with driver versions: in Nov 2025, AMD's Windows Vulkan driver beat Linux RADV by about 20% on prefill. On Linux, the ROCm-vs-Vulkan winner also changes with model and build. So "this Windows setup was slower than this Ubuntu setup" is true. "Linux beats Windows on Strix Halo for local LLMs" is a fair bet for prefill on current Mesa, but it is not proven by this test.

Where the 12.67 seconds went

Total time is roughly the time to first text (prefill plus overhead) plus the number of output tokens divided by the generation speed. On the long prompt:

Windows 11: 37.94 s
first text 26.77 s
writing 11.17 s
Ubuntu Vulkan: 25.27 s
first text 15.47 s
9.80 s

About 89% of the saving (11.30 of 12.67 s) came before the first word. As a rough rate (my arithmetic, which includes server overhead), about 6,303 tokens / 26.77 s ≈ 235 tok/s of prefill on Windows, against ≈ 407 tok/s on Ubuntu Vulkan. Generation rose only 15.22 → 16.66 tok/s. A short-prompt, long-answer workload would therefore show a much smaller gap than 33%.

4. Why gaps like this appear

  • Different Vulkan drivers. Windows uses AMD's own driver inside AMD Software. Linux uses Mesa RADV. Their speeds move with each release. RADV prefill trailed Windows on Mesa 25.0 and caught up by Mesa 25.3-devel (Phoronix, Sep 2025). In Nov 2025, Windows led on Strix Halo partly because its driver exposed bf16 and RADV didn't (recap). RADV got substantially faster again on Ubuntu 26.04 (Phoronix, 2 Apr 2026).
  • Memory allocation. On Windows the iGPU gets a fixed BIOS carve-out (96 GB max on these boxes). At 96 GB, AMD's Windows driver split it into 32 + 64 GB Vulkan heaps, and llama.cpp at first saw only 32 GB (issue #16832, Oct 2025, fixed by PR #17110). On Linux the GPU can also borrow system RAM through GTT, raised with ttm.pages_limit / ttm.page_pool_size. Jeff Geerling reached about 108 GB and notes that amdgpu.gttsize is deprecated (8 Aug 2025). This decides which big models fit, but it wasn't a factor here (about 28 GiB used).
  • Backend maturity on gfx1151. Early HIP prefill was poor until ROCBLAS_USE_HIPBLASLT=1 (issue #13565, May 2025). rocWMMA flash attention helps at long context (kyuz0). ROCm 7.x failed in 14 of 14 configurations on this exact Bosgame board (Frontier Lab, May 2026). Lemonade's docs list both ROCm and Vulkan on Windows and Linux, and tell Ryzen AI iGPU users to try ROCm first with Vulkan as a fallback (docs). Measured results often favour Vulkan anyway.
  • Different llama.cpp builds. Hardware Busters changed the build between runs and doesn't name the Windows one. llama.cpp ships many builds a week, and single PRs have moved gfx1151 prefill by 19–35% (Strix Benchmarks, PR #21344).
  • Prefill and decode are bound by different things. Prefill is compute-heavy and very sensitive to kernels and drivers. Decode is mostly limited by memory bandwidth, which is the same hardware on both OSes. A long-prompt test magnifies driver differences. That is why the total fell 33% while decode rose only 9.5%.
Speculation: the Windows short-prompt first-text time of 2.57 s for only 48 tokens (vs 0.315 s on Ubuntu) looks more like fixed per-request overhead in the Windows router, driver or settings than slow compute. The article gives no breakdown, so this is unconfirmed.

5. What it means for your Linux Strix Halo box

You're already on the faster side of this test, so nothing here speeds your box up. The real levers are a current kernel, Mesa and llama.cpp build, and testing both RADV and ROCm per model. Public results lean ROCm for dense-model prefill and RADV for MoE decode, but builds flip this. Turn on MTP where the model supports it, and raise GTT via ttm.pages_limit only if you need more than the BIOS carve-out.
